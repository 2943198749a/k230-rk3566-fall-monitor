# 系统架构与数据流

## 总体结构

```text
K230 RT-Smart 大核
  摄像头/VICAP
       │ RGB888P/帧缓冲
       ├──> ai2d letterbox ─> KModel/NPU ─> YOLO 解码/NMS ─> Fall/NoFall
       │                                                   │
       │                                                   └──> DetectionStatus
       │                                                        │ 状态 DataFIFO
       └──> OSD 绘框 ─> VENC H.264 ─> 视频 DataFIFO             │
                                      │                         │
K230 Linux 小核                       │                         │
                            rtspServer│              status_tcp_client
                                      │ RTSP                    │ TCP 文本
                                      ▼                         ▼
RK3566 Linux                  Qt + FFmpeg 播放器        status-service
                              视频、fps、重连           SAFE/FALL/UNKNOWN
```

## 为什么 K230 大核做 AI 和编码

摄像头 VICAP、视频缓冲 VB、硬件编码 VENC 和 nncase/NPU 都与 K230 媒体运行时紧密相关。大核使用 RT-Smart 能以固定 API 访问这些硬件，并减少帧在多个用户态网络进程间复制。主循环拿到帧后完成预处理、推理、结果绘制，再把最终图像交给编码器。

大核不是 RTSP 服务端。RTSP 涉及 socket、会话、RTP/RTCP 和客户端生命周期，更适合 Linux 小核运行的 Live555/KdRtspServer。DataFIFO 是两个 OS 之间的桥梁。

## 视频通道

编码器输出由一个线程读取。每个 DataFIFO 记录按以下逻辑组织：

```text
offset 0:  k_u64 pts
offset 8:  k_u32 encoded_length
offset 12: H.264 Annex-B bytes
```

视频 FIFO 单槽约 1,024,000 字节，共 10 个槽，足以容纳大多数 720p 编码帧。小核根据大核打印的物理地址用 `kd_datafifo_open_by_addr()` 打开同一个 FIFO。RTSP session 名是 `BackChannelTest`，默认端口 8554。

所有权顺序：

```text
大核 write + WRITE_DONE
    -> 小核 read 得到共享指针
    -> SendVideoData 使用该指针
    -> 小核 READ_DONE
    -> 大核 write(NULL) 回收已确认槽位
```

如果在 `SendVideoData` 前 `READ_DONE`，大核可以覆盖槽位；这类错误通常不是稳定崩溃，而是偶发花屏、解码报错或数分钟后中断，所以代码用 `dispatch_fifo_payload()` 固定顺序。

## 状态通道

状态使用独立 DataFIFO。记录的前 64 字节是 `DetectionStatus`：

```text
magic, version, sequence, total, standing, fallen
```

结构体 `alignas(64)` 且 `static_assert(sizeof(...) == 64)`，防止编译器或两端 ABI 差异改变布局。FIFO 槽固定 1024 字节，剩余部分清零。状态约每 30 次推理发布一次；FIFO 没空间就丢弃本次状态，不等待，因为“旧一秒状态”比“推理和视频被阻塞”更安全。

小核复制状态后立即释放共享槽位，再校验 magic/version/人数守恒，然后格式化：

```text
STATUS seq=81 total=4 standing=3 fallen=1 state=FALL\n
```

TCP 断线只关闭 socket 并重试，不关闭状态 FIFO，也不触碰视频进程。

## RK3566 状态机

```text
启动                       -> UNKNOWN（尚无合法状态）
收到合法 state=SAFE        -> SAFE
收到合法 state=FALL        -> FALL
连续 3 秒没有合法状态       -> UNKNOWN
UNKNOWN 后收到新合法状态     -> SAFE 或 FALL
```

`UNKNOWN` 是 RK3566 的本地健康状态，不允许 K230 从网络发来。这样能区分“模型明确判断无人跌倒”和“系统根本不知道现在怎样”。

## Qt/FFmpeg 线程关系

```text
GUI thread
  MainWindow -> PlayerController
                    │ queued signal
                    ▼
             decoder QThread
               RtspDecoder
               FFmpeg I/O/decode/sws_scale
                    │ QImage deep copy
                    ▼
GUI thread       VideoWidget::setFrame
```

FFmpeg 的上下文、packet、frame 和 `SwsContext` 全部在解码线程创建、使用和释放。跨线程只发送 Qt 值对象。`QImage::copy()` 使像素内存脱离解码循环，否则 GUI 可能绘制已经被下一帧覆盖的缓冲。

## 当前实现的兼容分支

Qt 工程里还有 `DetectionCountReceiver`，它监听早期 UDP JSON：`{"fall":1,"no_fall":2}`。这是历史兼容模块，不是当前 TCP `STATUS` 服务的接收实现。交付包保留它和测试，是为了完整呈现现有代码；如果要把 TCP 状态直接显示到 Qt，需要增加 Qt TCP/Unix Socket 接入层，不能假装当前已经完成。

## 故障隔离表

| 故障 | 视频 RTSP | 状态 TCP | 预期行为 |
|---|---|---|---|
| RK3566 播放器关闭 | 大核继续编码，小核继续服务 | 不受影响 | 再次连接即可 |
| RK3566 状态服务关闭 | 不受影响 | 小核重连 | 服务恢复后继续发送 |
| RTSP 服务退出 | 暂停 | 不受影响 | 重启时使用同一视频 FIFO 地址 |
| 状态客户端退出 | 不受影响 | RK3566 三秒后 UNKNOWN | 重启客户端恢复 |
| K230 大核退出 | 无新帧 | 无新状态 | 两通道均失效，需先重启大核并获取新地址 |
| 网络断开 | 客户端超时/重连 | UNKNOWN/重连 | 网络恢复后分别恢复 |
