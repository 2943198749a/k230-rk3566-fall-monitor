# 从零开始搭建 K230 + RK3566 YOLO 跌倒监控

## 1. 先把目标说清楚

系统需要同时完成四件事：摄像头实时采集、K230 NPU 跌倒检测、网络视频播放、检测状态可靠上报。把四件事全部塞在一个进程里会产生耦合：网络阻塞可能拖慢推理，视频解码可能卡住界面，状态断线可能误伤 RTSP。因此工程采用“双板、K230 双核、视频/状态双通道”的结构。

完成后的可观察结果是：RK3566 能连续播放 K230 的 1280×720 H.264 RTSP 视频；有人跌倒时检测框标记 `Fall`，状态服务收到 `state=FALL`；没有跌倒时为 `SAFE`；K230 状态链路断开超过三秒后 RK3566 显示 `UNKNOWN`，但视频仍可继续。

## 2. 硬件和软件分工

- K230 大核运行 RT-Smart，适合调用 VICAP、VB、VENC、nncase/NPU 等实时媒体和 AI 接口。
- K230 小核运行 Linux，适合 Live555/RTSP、TCP socket 和网络服务。
- RK3566 运行 Linux/Qt，负责用户界面、FFmpeg 解码和状态接收。
- PC/WSL 可先编译纯 C 状态服务与测试，但不能替代 K230 NPU、摄像头和硬件编码器测试。

准备以下内容：K230 开发板及摄像头、RK3566 Linux 板、两板可互通的以太网、与 K230 固件严格匹配的 K230 SDK、Xuantie RISC-V Linux 工具链、K230 RT-Smart 大核工具链、RK3566 上的 GCC/CMake/Qt5/FFmpeg 开发包。

## 3. 先验证网络，不碰模型

进入 `rk3566/status-service`。这里是从完整工程中提炼出的纯 C 学习层，不依赖 K230 SDK：

```bash
make clean
make
make test
```

第一个终端运行：

```bash
./rk3566_status_tcp_server 9000
```

第二个终端运行：

```bash
./k230_status_tcp_client 127.0.0.1 9000
```

模拟客户端会周期性产生 `SAFE` 与 `FALL`。停止客户端，服务端三秒后应显示 `UNKNOWN`。这一步先证明 socket、换行分帧、半包/粘包和超时状态机正确。若这一步失败，不应去调 NPU。

## 4. 理解并准备 YOLO 模型

部署模型位于 `k230/model/yolov5n-falldown.kmodel`。代码表明它是两分类、三尺度、anchor-based 的 YOLO 检测模型：类别 0 为 `Fall`，类别 1 为 `NoFall`；输出按 stride 8、16、32 解码，anchors 在 `falldown_detect.h` 中固定。

完整模型生产流程通常是：采集并标注 Fall/NoFall 数据 → 在训练机训练 YOLO → 导出 ONNX → 使用与目标 K230 SDK 匹配的 nncase 编译/量化为 KModel → 在 K230 上验证输入布局、输出顺序、阈值和类别。这个包没有训练数据、训练脚本、PT/ONNX 和原始量化配置，因此不要声称能复现训练；本包从已经生成的 KModel 开始，复现板端部署。

如果以后重新训练或转换，必须同步核对：

- 输入是 NCHW/CHW 还是 NHWC/HWC；
- 输入尺寸是否与 KModel `input_shapes_` 一致；
- 是否使用保持比例的灰色 114 letterbox；
- 输出张量顺序是否仍对应 stride 8/16/32；
- anchors、类别数和标签顺序是否一致；
- 量化类型和预处理均值/缩放是否与训练导出一致。

任何一项不一致，都可能出现“程序能运行但框完全错误”的静默问题。

## 5. 先跑独立模型，再接实时视频

`k230/bin/falldown_detect_standalone.elf` 和 `k230/model/examples` 用于最小化验证。把 ELF、KModel 和测试图复制到 K230 同一目录，并保留交付文件名：

```sh
mkdir -p /sharefs/app/falldown_model_test
cp falldown_detect_standalone.elf yolov5n-falldown.kmodel falldown_elder.jpg \
  /sharefs/app/falldown_model_test/
cd /sharefs/app/falldown_model_test
chmod +x falldown_detect_standalone.elf
./falldown_detect_standalone.elf yolov5n-falldown.kmodel 0.5 0.45 falldown_elder.jpg 0
```

示例脚本也默认使用 `falldown_detect_standalone.elf`；若文件放在别处，可用 `FALLDOWN_ELF`、`FALLDOWN_MODEL` 和 `FALLDOWN_IMAGE` 环境变量覆盖。独立图片推理正常后，再进入完整 RTSP 链路；这样可以把“模型问题”和“媒体管线问题”分开。

## 6. K230 大核部署工程怎样工作

`k230/big-core/main.cc` 的启动顺序是：

1. 校验四个参数：KModel、目标阈值、NMS 阈值、调试等级。
2. 初始化 VB 公共缓冲池，创建 H.264 Main Profile、CBR、1280×720、约 4 Mbps、30 fps 的 VENC 通道。
3. 创建视频 DataFIFO，打印物理地址，启动 VENC 输出线程。
4. 启动 VICAP，映射推理/OSD 所需的物理缓冲。
5. 加载 KModel，构造 ai2d 的 letterbox 预处理。
6. 循环抓帧、复制到 nncase 输入、运行 NPU、取三尺度输出、解码并 NMS。
7. 把 `Fall/NoFall` 最终框画到 OSD 图像，再送入编码通道。
8. VENC 线程把 H.264 header 和 frame pack 写入视频 FIFO。
9. 每约 30 个推理序列发布一次 64 字节检测状态到独立状态 FIFO。
10. 收到 `q` 后按线程、编码器、FIFO、VB 的逆序释放资源。

为什么每秒左右发布一次状态而不是每帧发布？状态只是当前摘要，30 fps 全发会增加跨核 FIFO 和网络负担；如果小核尚未启动，状态 FIFO 也更容易塞满。视频仍按编码器帧率输出。

## 7. K230 小核为什么分两个进程

`rtspServer` 只读视频 FIFO、维护 RTSP 会话。`k230_status_tcp_client` 只读状态 FIFO、连接 RK3566。这样 RK3566 状态服务停止时，状态客户端可以独立重连，而 RTSP 不需要重启；反过来，播放器断开也不会停止推理和状态上报。

DataFIFO 是共享内存所有权协议，不只是普通队列。读取方从 `kd_datafifo_read()` 得到的指针只在 `DATAFIFO_CMD_READ_DONE` 之前有效。RTSP 服务必须先调用 `SendVideoData()` 消费帧，再确认 `READ_DONE`。顺序反过来会允许大核复用槽位，造成花屏或损坏码流。

状态客户端采用另一种安全方式：先把 64 字节 `DetectionStatus` 复制到本地结构体，再 `READ_DONE`；之后校验和 TCP 发送都使用本地副本。

## 8. RK3566 接收与显示

状态服务将 TCP 当作字节流，而不是“每次 recv 就是一条消息”。它把收到的字节追加到 `LineBuffer`，按 `\n` 提取完整行，因此能处理半包和粘包；解析器还验证字段、数值和人数守恒。

Qt 播放器用 FFmpeg 打开 RTSP。解码发生在工作线程，GUI 线程只接收深拷贝后的 `QImage`。FFmpeg 中断回调读取原子停止标志，防止断网或关闭窗口时永远卡在 `av_read_frame()`。

## 9. 推荐实施顺序

严格按下面顺序联调，每一步只引入一个新变量：

1. PC/WSL 跑纯 C 协议测试和模拟客户端。
2. 两板互 ping，确认端口 9000 和 8554 没有被防火墙拦截。
3. K230 独立图片 YOLO 推理。
4. K230 大核只验证 H.264 与视频 FIFO，RK3566 用 ffplay 连续播放两分钟。
5. 启用状态 FIFO，在小核只打印读取到的结构体。
6. 启动 RK3566 状态服务，再启动 K230 状态客户端。
7. 同时运行 RTSP 和 TCP，验证任一通道断开不影响另一通道。
8. 最后启动 Qt GUI，验证停止、用户点击重连、断网后手动恢复和窗口关闭。

## 10. 何时算完成

不是“能看到一帧”就完成。完整验收至少包括：连续视频两分钟无花屏；`SAFE → FALL → SAFE` 可重复；停止状态服务后视频仍在；重启状态服务后客户端自动重连；停止 RTSP 后状态仍在；断开 K230 后三秒进入 UNKNOWN；Qt 停止和关闭不残留解码线程。详细用例见故障排查与验收文档。
